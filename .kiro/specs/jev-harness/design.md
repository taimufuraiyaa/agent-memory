# Jev Harness Technical Design

## Current baseline and ownership

`internal/api/server.go` serves the local Go API; `tools/agent-memory/mcp-server/src/server.js` is a Node stdio-to-HTTP adapter with default/expanded memory tool profiles. `internal/clientprofile/store.go` records client IDs and profile names but does not authenticate a caller. `internal/workspace` records project roots. Existing solution episodes hold concise durable paths, not raw harness turns. SaaS has been removed. These are compatibility boundaries, not a runnable harness.

The new inward `internal/harness` package owns stable identities, provider ports, access and outcome types, and a deterministic registry. Later Go application/runtime components own run orchestration and policy. Jev, model, and tool adapters point inward; the local API and MCP adapter point to the runtime. Core must import no concrete provider or transport. The composition root registers factories and fails on duplicate IDs.

## Contracts and lifecycle

All cross-boundary requests carry a contract version, provider identity, workspace, run/connection generation, bounded payload, and context cancellation. Static manifests declare potential capabilities; live snapshots declare current access and revision. Unsupported, unavailable, denied, stale, partial, timeout, cancelled, and failed are distinct typed outcomes. Results that mismatch provider, scope, or generation are rejected before orchestration consumes them. Manifests are discoverable without provider I/O; live access may be refreshed with a deadline. Provider sessions are disposed on cancellation, reconnect, or generation change.

A scoped session is the only path the run loop uses to reach a provider. Opening one probes live access for a workspace generation and keeps at most one open session per provider and workspace: a newer generation disposes the previous session and cancels its in-flight calls, while an older generation is rejected as stale before any provider work. Every request is shape-checked first (candidate, evidence, schema, token and argument counts and sizes, control characters, duplicates) so an invalid request never reaches a provider. A capability that is unsupported, denied or unavailable yields that typed outcome without a provider call. Each call runs under the caller's context, a per-session deadline and session disposal; a provider that ignores cancellation cannot hold the loop because the call returns a typed timeout or cancelled outcome and the abandoned work finishes on its own. Provider panics and transport errors become a failed outcome with no provider text. Replies are validated for scope, generation, revision and size before the caller sees them, and only ok and partial outcomes retain payload, so a denied, stale or failed reply cannot be mistaken for a result. A model asking for a tool it was not offered is rejected. Tool preparation returns a digest-bound handle that the same session can invoke exactly once; replays, forged digests and altered envelopes fail closed, a mismatched attempt does not consume the genuine handle, and outstanding handles are bounded. Approval and policy sit between preparation and invocation and remain the caller's responsibility. A conformance fake package with scripted misbehavior lets later real providers prove the same contract without editing shared orchestration.

The core keeps decision questions separate from model generation and tool preparation/invocation. Jev recommendations are advisory. The runtime validates candidates against live access, sensitivity, budgets, and deterministic policy. Tool adapters prepare native actions, while shared policy owns approval, audit, execution coordination, and postcondition verification. No provider name is hard-coded in shared routing.

## Run and API shape

The runtime will use a versioned state machine and transient repository for bounded chunks, events, checkpoints, idempotency keys, and artifact metadata. It will create concise solution-episode steps through the existing admission path, not copy raw prompts. The API namespace is `/api/v1/harness`. The opt-in MCP tools are `harness_capabilities`, `harness_start`, `harness_status`, `harness_continue`, `harness_artifact`, and `harness_cancel`. The Node adapter only forwards authenticated, schema-bounded calls. Start is asynchronous; status uses opaque, client-bound cursors. Disabling the feature prevents new runs while leaving existing memory tools unchanged.

Client authority is a separate local package outside the harness core. Grants are minted only by a trusted local CLI and never through MCP; the capability pack is off until enabled and disabling it denies every verification while still allowing revocation. A grant carries a registered client ID, one or more registered workspaces with the canonical root recorded at mint time, an operation allowlist, an expiry and a revision; approval is not an operation, so no credential can approve a mutation. The bearer secret is random, shown once, and only its SHA-256 is stored in a private user-level file (0700 directory, 0600 file, atomic replacement, symlinks, loose modes, unknown fields and future schemas rejected). Verification re-reads the grant file and the workspace and client registries on every call, hashes and compares in constant time even for unknown grants, and returns a single uniform denial for malformed, unknown, wrong-secret, revoked, expired, disabled, cross-client, ungranted-operation, unbound-workspace, deleted-client, changed-root and storage-fault cases, so nothing about which grants exist is disclosed. The project root in the verified identity comes from the registry, never the caller. Rotation replaces the secret and bumps the revision so the old token and any approval bound to the old revision stop working; bindings are not silently re-blessed, so a changed root requires revoke and mint. Mutations take an exclusive cross-process lock so a revocation is not lost to a concurrent write. The alternatives of treating a client profile ID as authority, storing a recoverable token, and exposing minting over MCP were rejected. A coding agent with unrestricted shell access runs as the user and is outside this boundary; the protection is against MCP-reachable callers, not a compromised local account. Existing client profiles are untouched, and an expanded tool profile confers no harness authority. Rollback disables the pack; grants remain inert and revocable.

The run runtime is a Go package that owns a versioned state machine and a private transient file repository, both separate from durable memory. A run moves through queued, running, needs-attention, cancelling and the terminal states completed, partial, failed and cancelled along a fixed edge table; terminal states have no exits, and running may return to queued only for crash recovery and clarification resume. The generation increments on state changes, not on usage updates, so a client's expected generation stays valid while work proceeds; a separate epoch increments each time a worker takes the run and scopes its provider sessions, so a resumed run supersedes only its own sessions and concurrent runs in a workspace stay independent. Every mutation requires a client idempotency key and the generation the client last saw. Replays return the recorded outcome, a reused key with a different request is a conflict, a stale generation is rejected, and start deduplicates by client, workspace and key through an atomically published record so concurrent starts create one run; a claim whose run does not exist yet is awaited while fresh and reclaimed only when stale. A run is visible only to the client and workspace that started it, and every other caller receives the same not-found result as for a missing run. Start persists a queued run and returns at once; a bounded worker pool takes it, and a full queue is reported before any state is committed. The loop makes one model call and at most one tool action per turn, always through harness sessions, and commits after each reply so a restart replays at most the interrupted call. Budgets cap turns, active provider time, tool calls, output bytes, spend and recursion depth, with defaults and a hard ceiling; hitting one ends the run as partial and keeps the latest model text as an artifact, never as a failure. A child run is capped by the parent's depth limit and inherits only the parent's unused budget. Cancellation of a running run moves it to cancelling and cancels the provider calls it has in flight; a queued or waiting run is cancelled directly; a manager shutdown is not a cancellation and leaves the checkpoint for recovery. Recovery requeues running runs from their checkpoint with consumed budget intact, finishes runs that were cancelling, and quarantines damaged records instead of trusting them. A model can ask the client a question through a reserved clarification tool, which parks the run for an answer through continue; an approval requested by tool policy parks the run for a trusted local channel and continue can never satisfy it. The default tool policy denies everything. Status and event pages carry state codes and counters, never goals, prompts or provider output; event cursors are opaque, signed with a persisted key and bound to one run and client, and the bounded event ring reports a gap rather than silently skipping. Untrusted text is redacted before it is bounded and kept, and goals, inputs, model text, tool output and artifacts are all treated this way. Retention is separate from durable memory: finished runs expire after a short window and abandoned runs after a maximum age, active runs are never removed, and idempotency records follow their runs. Only fixed, content-free summaries are offered to the solution-episode sink. Rejected alternatives were persisting the loop in the MCP adapter, bumping the generation on every usage update, and treating shutdown as cancellation.

The first transport slice exposes only capabilities, start, status and cancel through the local Go API and four opt-in tools in the Node MCP adapter. The Go routes are registered only when a gateway has been composed, so an unconfigured install exposes nothing, and composition itself requires an explicit provider setting that currently accepts only scripted fakes; capability discovery marks them as fake and never describes them as real. Every route authenticates a bearer grant for exactly one operation in one workspace through the credential authority, reads the token only from the Authorization header, and answers every failure with one identical denial. The grant's client, not a caller-supplied header, is the run owner; the optional client header is only a claim used to detect a mismatch. Bodies are size-bounded and strictly decoded, errors map to fixed codes and messages, and a storage fault is an opaque internal error. The client view of a run omits the approval action digest, since only the trusted local channel needs it. The shared client profile store backs both the profile API and the authority, so removing a profile revokes access at once, and the run manager consults the authority before every turn so revoking or disabling a grant stops running work. The adapter's tools exist only when a harness grant is configured, validate every argument locally against bounded schemas before any request, build paths only from validated identifiers, refuse redirects so the grant cannot be forwarded, scrub the grant from any error text, and refuse oversized results. A malformed grant makes the adapter exit at startup without echoing it. Continue, events, artifact and approval are deliberately not routed in this slice. A terminal or parked state is published only after the run's provider sessions have been released, bounded by a close timeout so a hung provider cannot hold a run hostage, which lets a client rely on a stopped run having no provider work left. Rejected alternatives were accepting the grant in a query string, deriving identity from the client header, registering routes unconditionally, and exposing an approval tool.

Context assembly is a separate Go package that turns candidate evidence into one prompt-ready selection. Adapters report chunks carrying workspace, source, a locator and exact revision, sensitivity, trust, relevance and lifecycle; the coordinator excludes by fixed reason codes, never by content: wrong workspace, a class above the provider's eligibility, a superseded or expired lifecycle, a duplicate, an invalid record, a source whose current revision no longer matches what was read, and anything that does not fit. Trust says who wrote a chunk, never what it may do: the run goal and the client's answers are the user's words, checked-in instruction files are project-owned, and everything else, including repository files, recalled memory and model or tool output, is untrusted. Only user and project chunks can be pinned, an untrusted chunk's pin is ignored, and pinned instructions are always shown in full or the assembly fails loudly rather than dropping them. Prompt text, evidence, pinned items, tool schemas and reserved output share one budget; the fixed policy preamble and every provenance header are charged to it, each item is sized on the exact block that will be rendered, and the total can never exceed the limit. Secrets are redacted before text is bounded, so a secret cut by the bound leaves no recognizable fragment, and summaries and header fields are redacted too. Output is deterministic and independent of input order. Each chunk is shown at full, long or short visibility chosen from its relevance and stepped down under pressure, and hidden only last. A decision advisor such as Jev may nudge the order but only through opaque chunk IDs, sizes and coarse relevance, never text, titles or paths, only for chunks within the advisor's own egress class so the existence of a more sensitive chunk is never revealed, over at most a fixed number of candidates and under a deadline. Its answer must be a duplicate-free subset of what it was offered with sufficient confidence; promotion is a bounded boost, not an override, so it cannot unhide, widen access or exceed the budget, and any failure, timeout, panic or malformed answer leaves the deterministic assembly unchanged. The rendered prompt states a fixed trusted policy, lists pinned items under INSTRUCTIONS and everything else as evidence under a per-assembly random boundary, and prefixes every body line with a quote marker, so no line of evidence can resemble a header or a section edge; header fields are single-line and redacted. Instruction-like text in untrusted content is flagged for review but flagging is a signal, not the defence: the defence is structural quoting plus the fact that no text grants authority, since tool access and approval come only from Go policy. Repository files are read through an operating-system root-confined handle, so symlinks and parent traversal cannot escape the project; hidden entries and credential-like names are refused, only regular text files are opened so a FIFO cannot hang the reader, and reads are size-bounded. A blocked instruction file is reported rather than silently skipped. Rollback is to run the loop without a context source, which falls back to its own references, or without an advisor, which uses the deterministic order.

Model routing and accounting live in a separate package so the run loop stays provider-neutral. A provider's static profile, supplied by the operator, states its price per million tokens for uncached input, cached input and output, the most sensitive data class it may be sent, its context window and its output cap. A profile is configuration, not proof of access: every selection probes live access through a real provider session, briefly cached, and an undeclared, denied, unsupported or unreachable capability is excluded. A provider is eligible for a call only when its capability is live, the data class of the assembled prompt does not exceed its class, the call fits its window and output cap, it is not cooling down after repeated failures, and its estimated cost fits the run's remaining spend. The eligible providers are ranked by estimated cost, then smoothed observed latency, then identifier, and the ranked list, capped in length, is the only fallback chain: a failure moves to the next eligible provider and can never reach one that was excluded for this data, so restricted data with no eligible provider fails the run with an explicit code rather than being sent anywhere. An advisor may name one eligible provider to try first, seeing provider identifiers only and never the task; its answer must be one of the eligible providers with enough confidence, and any failure, timeout or malformed answer keeps the deterministic order. Every attempt, including a failed one, is accounted for, because a failed call can still cost money and time: tokens and spend accumulate on the run, and a failed attempt is added before the next is tried. A budget-driven timeout ends the run as partial instead of trying another provider. Prompt caching is never assumed. A cache saving is credited only when the request carried a stable prefix identity, the call completed, and the provider itself reported cached input tokens; the identity is a hash of the fixed policy, the per-run boundary and the pinned items exactly as rendered, so it is the same on every turn of a run while the pinned part is unchanged, and the leading bytes of the prompt really are identical. The router estimates a discount only from what that provider reported for that same prefix on an earlier call, and retrieval caching is never counted. Cost arithmetic bounds every input so token counts times prices cannot overflow, rounds up to a whole micro unit, clamps at the contract maximum, and treats malformed usage as free rather than negative or overflowing. A journal of recent observations can be replayed under the prices in force to reproduce recorded cost exactly, or under new prices to show what the same traffic would cost. The first real provider is text-only: it sends one stateless request with only the model, the assembled prompt, the output cap and the store and stream switches turned off, never offers tools, accepts a dated snapshot of the configured model, maps every service response to a typed outcome without carrying service text, the key or the prompt, refuses redirects, bounds its reply to the envelope on a character boundary and estimates cost from sizes when a response omits usage. It refuses to exist without an explicit egress opt-in, and its composition requires the key, the model, the egress confirmation and operator-supplied prices, caps the data class at internal, and defaults nothing that could widen egress or misreport spend. A conformance suite applies the same contract checks to two differently shaped fake families and to the real adapter against a fake service. Rollback is to leave the provider setting unset, which composes nothing.

Project tools are staged by risk, and the first stage is read-only. All project file access goes through one confined-filesystem package: every open uses an operating-system root-confined handle, so a symlink or parent traversal cannot leave the registered root, paths that are absolute, contain NUL or are too long are invalid, hidden entries and credential-like names are denied, only regular text files are opened so a FIFO or device cannot hang a reader, binary files are refused, and every read is size-bounded. A relative link that stays inside the root is followed, while an absolute-target link is refused even when it points back inside, which is the conservative choice. The context assembler and the tools share this package rather than keeping two copies of the security-critical code. The read provider offers three tools, read a file by line window, list a directory, and search by literal or regular expression, and a deny-by-default tier policy classifies each by capability: read tools are allowed, a tool nobody classified is denied, an action that did not prepare successfully is denied, and an ask tier exists for the later mutating tools. Preparing a call validates its arguments strictly with unknown fields, trailing data and out-of-range values rejected, returns a typed denial for a protected path and a typed failure for bad arguments without saying why, reads nothing, and remembers only the normalized call; the digest binds the tool, the normalized arguments and the project root. Invoking resolves the root again, so a workspace re-pointed since preparation is stale rather than read, consumes the remembered call so it cannot be replayed, and re-reads through the confined handle. Output is untrusted evidence: it is redacted, stripped of control characters, line-capped, deterministic and fitted to the reply envelope, with anything cut reported as partial. Search uses a linear-time regular-expression engine so a hostile pattern cannot stall it, skips dependency and build directories, hidden entries and non-regular files, never follows symlinks, and is bounded by result count, file count, per-file and total bytes and wall time, reporting how much it scanned and skipped and whether it stopped early. Results are ordered by full path rather than walk order so they are stable. Git is deliberately not part of this stage: even read commands such as status and diff run clean filters, drivers and monitors named in the repository's own configuration, so on a hostile clone a read could execute arbitrary commands. Git moves to a later stage that first refuses repositories whose configuration names such things. Rejected alternatives were running git for reads now, duplicating path checks in each tool, and string-based path checks without a confined handle.

Client capability credentials must be minted and verified by Go, bound to client ID, allowed workspaces/operations, generation, and expiry. The registered workspace supplies the project root. Revocation invalidates access and pending approvals. Trusted UI/CLI approval is a separate operation and cannot be synthesized by model-callable MCP tools.

## Context, models, tools, and failure modes

Evidence adapters gather eligible memory, solution, repository, instruction, and run chunks. A context coordinator budgets all chunks and tool schemas together, uses Jev visibility advice when valid, and otherwise follows deterministic relevance. Active instructions are pinned. Source revision/provenance survives compaction. Data classification gates provider egress; prompt injection in a file cannot change authority.

Model adapters report live capability, data-class eligibility, usage, cost, latency, and cache metrics. Cache reuse is considered only with a stable prompt-prefix identity and actual provider cache accounting. Tool adapters offer snippets, schemas, and on-demand detail; validated arguments are confined to registered roots. Prepared edits/commands are rechecked immediately before execution. An unavailable model can fall back only to another eligible provider; an unavailable Jev decision can fall back only to a bounded deterministic choice. Failed, partial, timed-out, and stale results remain visible as typed states, not empty success.

### Guarded edits and trusted approval (task 7b)

Mutation is a separate stage that ships behind its own switch: with it off the provider offers no edit tool, and a tool nobody classified is denied. Three tools exist, `edit_file` (one to twenty exact-text replacements, each of which must match exactly once in the original file and must not overlap another), `create_file` (a new file, creating missing parent directories) and `delete_file` (a regular file). Rename is not offered; it is a create plus a delete and each half is reviewed. Every tool validates its arguments strictly, refuses hidden and credential-like paths and any path with a link in an existing component, refuses binary, non-UTF-8 and oversized content, and prepares without touching the disk beyond reading the current file. Hidden control-plane locations (`.github`, `.gitignore`, `.kiro`, `.claude`, `.git*`) are denied outright rather than asked about: the read tools already refuse them, an edit made without being able to read the file is blind, and a later stage can open them deliberately.

An approval is decided only by a person at a local terminal. The decision is a record in a private approval store (0700 directory, 0600 files, atomic replacement, cross-process lock) written by `agent-memory harness approvals approve|deny`, which requires an interactive terminal on both input and output, shows the reviewed change, and requires the person to type a short code derived from the approval and its digest. Running the command with piped input is refused. The run manager never receives an approval over a call: it reconciles recorded decisions, so there is no manager method, HTTP route, MCP tool or grant operation that approves anything, and a test asserts none exists. A decision applies only when the run is still waiting on exactly that approval, at the generation recorded when the run parked, for the same client, workspace and grant, and the grant is still valid; revoking or disabling the grant records the approval as revoked and cancels the run. The boundary is between callers reachable through MCP and the local person; a process running as the same operating-system user can write the store directly, exactly as it can edit the files, and is outside this boundary.

An approval record binds the run, its generation, the client and grant, the tool, the exact normalized arguments, the paths touched, the reviewed preview, an expiry (thirty minutes by default) and an action digest. The digest covers the tool, the canonical arguments, the project root and the current revision of every file touched (the content hash, or an explicit absent marker), so the diff the person reviewed is computed from the same bytes the digest names. The preview is a unified diff built from the edit ranges, with control, bidirectional and zero-width characters shown as visible code-point markers so nothing is hidden from the reviewer. A record moves pending to approved or denied (or expired, revoked or superseded), approved to consumed exactly once, and keeps its content only while pending: arguments and preview are cleared when it resolves, leaving digests, paths and outcome for the audit. Consumption is recorded before the action runs, so a crash can lose a result but can never apply the same approval twice.

Policy classifies by capability and by the paths the prepared action reports. Edits and creates ask every time. Deletes, anything under a control-plane name (dependency manifests and lockfiles, build and CI scripts, Dockerfile and Makefile, shell scripts, migrations and schemas, instruction files), large changes and anything the preview had to truncate ask with extra friction: a longer code, a stated reason, and never any batching, since an approval covers one action. A mutating capability configured as allowed is clamped to ask, so a misconfigured table cannot run an edit unprompted.

The run loop parks a run that needs approval with an opaque approval identifier and no content, and an approved run first replays exactly the approved call: it prepares the stored arguments again, requires the digest to be identical (any file that changed since the review makes it stale and the model sees a stale result instead of a write), re-asks policy, and only then invokes, under an approval proof that only the manager can mint. The provider refuses a mutating call without that proof, so a policy bug alone cannot write a file. A denial returns a result to the model so it can choose another course, or with the stop option cancels the run. Immediately before replacing a file the provider rereads it and compares revisions, writes a temporary file in the same directory with the original permissions, replaces atomically, and rereads the result to verify its hash, restoring from the saved pre-image if verification fails. Before any replacement it saves the pre-image keyed by the action digest, which `harness approvals undo` uses to restore a file only if it still has the revision the edit produced. Every request, decision, application and undo appends a content-free line to a hash-chained audit log.

Three details keep this honest. The record stores the arguments as the exact bytes the model sent, because re-encoding them could change a digest computed from them and make an approved action silently do nothing. A provider that keeps state for a prepared action can release it when policy or approval declines the action, so declined calls cannot fill its bounded table. And because an approval is recorded a moment before its run parks, the manager that applies decisions treats a run that is still running as possibly about to park for a grace period, and ends an approval only when its run has finished, parked on something else, or stayed silent past that period. A failed preparation can also carry a fixed reason code, such as `no_match`, so a model can correct itself without any file content reaching it.

Rejected alternatives were approving through an MCP tool or a flag on continue, a long-lived grant for edits, a plan-level approval of many actions, trusting the provider's own claim that a path is sensitive instead of classifying in policy, running edits in a scratch copy and merging, and shelling out to `patch` or `git apply`. Known limits: the recheck and the replacement are not one atomic step, so a local process racing the write can win the gap; permissions beyond mode bits, extended attributes and ownership are not preserved on replacement; Windows behavior is untested; a run interrupted between consumption and result loses that result.

Workers share only authorized read snapshots, inherit budgets, and register deduplicated subgoals. Concurrent writes use ownership locks or isolated branches and revision checks. Cancellation tears down model, Jev, tool, and worker operations. A budget stop produces a partial result with usable artifact references.

## Local Jev credential setup

The Bubble Tea TUI gains a Jev setup destination. It renders only a configured flag and never a token, prefix, length, or untrusted error detail. Text entry remains masked, has an explicit size bound, and clears its draft on save/cancel. Removal requires a separate confirmation. Credential operations are injected behind a narrow TUI port; the provider-specific local store lives outside `internal/harness` core. The store uses a user-level private directory (0700), one regular credential file (0600), atomic replacement, and rejects symlink or loose-permission paths. It is not placed in `config.yaml`, a workspace database, logs, or MCP results. Read failures fail closed. The TUI only stores/removes credentials; it does not call Jev or declare the token valid. The TUI command remains local-only and requires an interactive terminal.

The alternative of adding the token to general YAML config was rejected because workspace configs and diagnostics may be shared. An OS keychain could improve at-rest protection on a single platform but would complicate portable local installs; a private file is the current local-product pattern. The user must treat local account compromise and filesystem backups as outside this file-permission boundary. Rollback removes the screen; the credential file can be removed through the TUI or manually by its exact path.

## Verified TypeSafe Jev decision adapter and Claude advisory opt-in

### Host-scoped model candidates

A private user-level JSON catalog (`model-catalog.json` in the Agent Memory data directory) has a version and separate `claude` and `chatgpt` candidate arrays. Each entry carries an opaque exact model ID and a short task-fit description; it does not carry credentials or claim live availability. The shared loader rejects symlinks, broad permissions, duplicate IDs, unknown hosts, oversized or malformed content, and fewer than two candidates in a host selection. The decision service creates one typed Jev choice from only the requested host's entries and a redacted bounded task, then validates confidence and exact membership. The Claude hook can consume this as additional advisory context when Jev listening is explicitly enabled. A host-facing CLI selector can return the same structured choice for an external dispatcher, but neither Claude's `UserPromptSubmit` nor a ChatGPT conversation is silently switched. A future harness dispatcher must separately prove live model access, policy, budgets, and supported host control before execution. Rollback removes the catalog or disables Jev; local recall remains unaffected.

`openai_api` is a third host identity in the same versioned catalog. It is deliberately separate from `chatgpt`: the latter expresses the app model-picker choices, while the former is an allowlist for API requests under an independent API key. A small OpenAI-native adapter owns fixed-endpoint model probe and one stateless Responses call, with a separate hard timeout, no redirects, no tools, no persistent conversation, strict input/output bounds, `store:false`, and sanitized errors. The CLI orchestrator requires an explicit invocation and egress flag, checks registered-project scope, performs the Jev choice, then probes and sends only the selected model. Failures never retry a different model or switch the ChatGPT app. The public API model's availability is proven live at request time, not inferred from the app or catalog. A text-only response is not a full coding harness; that remains task 6.

TypeSafe's published OpenAPI identifies `https://api.typesafe.ai/v1/systemone` and `/v1/models`, bearer authentication, `jev-latest`, typed choice questions, and typed answers. A leaf adapter owns HTTP, authentication, response decoding, deadlines, size limits, candidate-set validation, and non-sensitive errors. This Claude-specific advisory slice consumes the leaf behind a narrow choice interface; registration into the broader provider-neutral harness decision port remains part of task 8, after the run authority and scope contracts are operational. No OpenRouter key is inferred from a TypeSafe token.

The existing project-scoped Claude listen state gains an independent `JevEnabled` preference, default false and removed on listen-off. Explicit `/am listen all` maps to CLI `listen on --jev`: it checks project scope, credential presence, and live model access before enabling local listening and Jev together; plain `/am listen` maps to `listen on` and keeps remote egress off unless already separately consented. `/am listen off` disables both; status exposes both. Existing Jev commands remain compatibility aliases. A failed Jev probe leaves prior state untouched. On a prompt, the hook first enforces the registered root, strips recognized secrets/private spans, and limits the text and local project skill catalog before sending anything to Jev. It asks choice questions for `light|standard|deep` task complexity and, if non-AM project skills exist, one skill name or `none`. A result is advisory context only; Claude can decide whether to use a skill, and no hook-initiated model switch is claimed. Timeouts, unsupported models, malformed probabilities, unknown skill names, low confidence, and service failure suppress Jev advice while keeping local recall. No raw provider response or credential is logged or persisted.

Alternatives rejected: treating a stored token as ready, sending every prompt when only local listen is enabled, using OpenRouter with the TypeSafe key, or automatically mutating Claude's selected model. Rollback turns Jev preference off without touching local recall or the stored credential. Live probe costs no decision request; prompt decisions may incur provider usage after the explicit opt-in.

Interactive install and upgrade reuse that credential store after their primary setup transaction succeeds. A small terminal-only onboarding function checks configured status, asks a default-no approval question, reads an approved token without terminal echo, and stores it through the same validation/atomic path. On upgrade, the step is offered only if the store reports no configured token; unsafe credential state is an error, not permission to overwrite. EOF or decline skips without mutation. Errors in approved secret entry or storage report a safe credential-setup error without the token, while the already completed install/upgrade remains intact. The interactive terminal gate requires both input and output TTY; JSON output, dry run, hooks-only, and headless automation never call the prompt. The alternative of adding a Jev row to the existing component picker was rejected because the token is a user-level secret, not an installed package or model. Rollback removes the post-setup prompt; the TUI remains the manual setup path.

## Claude subagent model routing

Claude Code's `PreToolUse` hook on the `Agent` tool can replace the full tool input before the subagent starts; the Agent input includes an optional per-invocation `model`. This is distinct from switching the main session. The managed hook must match `Agent` exactly and have a deadline long enough for one bounded Jev request, while unrelated lifecycle capture keeps its existing timeout. The hook loads registered-root and Jev-listen state before reading credentials or making provider requests. It sends only a redacted, UTF-8-bounded `tool_input.prompt` plus the private Claude-host candidate ID/description list. No source files, other tool parameters, or raw responses leave the machine. The chosen ID must pass catalog membership and confidence checks. The output preserves all original Agent fields and changes only `model`; it never emits `permissionDecision: allow`, so Claude Code's normal permission policy remains authoritative.

An invalid/missing prompt, wrong root, missing catalog, provider failure, low confidence, or deadline emits no input update and leaves the original Agent call intact. This fail-open choice preserves normal delegation without claiming Jev routing. Existing model overrides may be replaced when Jev returns a valid choice because Jev is the explicit opt-in model selector; no other arguments are changed. Claude Code may still substitute an unavailable model under its own `availableModels` policy. A later `PostToolUse` Agent result can report `resolvedModel`, which is the reliable host observation; a pre-tool status can only say that Jev requested a model. Keep raw task text, tokens, and provider response out of logs. Rollback disables Jev listening or removes only the managed Agent-specific hook group. Automated verification uses fake Jev answers and JSON contract tests; a live Claude session and cost/latency comparison are separate release evidence.

Alternatives rejected: `UserPromptSubmit` cannot rewrite Agent input, `SubagentStart` occurs too late and only injects context, and rewriting a skill or shell-driving `/model` would alter the main session or rely on undocumented behavior.

## Claude Code listen bridge

Claude Code already has an Agent Memory MCP entry and a managed `UserPromptSubmit` hook. Its documented hook can add context or block a prompt, but cannot replace it or initiate a model switch. Keep that host-specific behavior in the Claude adapter; reuse the existing local Agent Memory recall service and policy rather than building a second orchestrator in the hook. The `/am` project skill is user-invocable only and controls an explicit per-workspace opt-in through the CLI. It must not be mistaken for a universal slash command or a Jev runtime. A later decision adapter may add skill/model recommendations to the same typed host-context boundary, subject to provider eligibility and consent; host-model switching still needs a separately supported Claude control path or task delegation to the Agent Memory harness.

The listener state is local user configuration, bound to a registered workspace and canonical project root, not a token or a run record. The prompt hook checks that binding on every event, redacts and bounds task text before local recall, and emits Claude's `hookSpecificOutput.additionalContext` with a concise source label. It never puts raw provider results or a CLI success envelope into prompt context. Listener errors/timeouts fail open with no injected context; no raw prompt is logged by this bridge. Connection writes only a managed skill and reuses the existing hook; existing `am` skills are not overwritten. Disconnect removes only matching managed content. Settings/readiness distinguish disabled, listening-with-memory-context, and future Jev-decision availability. A project not registered to a root cannot enable listening.

Alternatives rejected: global unconditional prompt forwarding (privacy and cross-workspace ambiguity), a shell-substitution skill that interpolates user arguments (injection risk), and claiming `UserPromptSubmit` can change Claude's model (not in the host contract). Verification includes skill discoverability, idempotent connect/disconnect, user-content preservation, root mismatch, missing local service, redaction, bounded output, and explicit non-Jev readiness. Rollback disables the local listener and removes the managed skill without touching existing Agent Memory memory hooks.

## Alternatives, risks, and rollout

Putting the loop in Node was rejected because it would split authority and persistence from Go. Reusing memory retrieval cache as model prompt cache was rejected because their identities and metrics differ. A single large provider interface was rejected because partial providers would need meaningless methods. An MCP `approve` tool was rejected because model-callable control is not trusted human intent.

Key risks are an unverified Jev API, client-profile IDs being mistaken for credentials, filesystem escapes, stale approvals, provider data egress, unbounded prompt/tool output, and checkpoint incompatibility. Address them with contract fakes first, auth before transport exposure, path/revision tests, classified egress, size budgets, and versioned restart fixtures. Roll out behind an opt-in capability: contracts, fake MCP-to-Go slice, read-only real model/tool flow, guarded mutation, full Jev decisions, then workers. Disable each capability independently and keep existing local memory paths intact.

## Verification

Conformance covers duplicate registration, static/live capability differences, full/partial/denied/unavailable/malformed/slow/disconnecting providers, scope and generation mismatches, cancellation, and bounded output. Later integration tests cover auth, MCP reconnect, idempotency, restart, approval replay, symlink escape, client isolation, privacy, and one real coding run.
