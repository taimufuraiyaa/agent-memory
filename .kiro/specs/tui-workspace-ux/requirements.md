# Terminal Workspace UX

## Objective and authority

The user's 2026-10-11 request authorizes redesigning the installed Go TUI to be usable and helpful like the former workspace UI. This extends tui-primary-interface while preserving its local/remote transport, installed start/restart, safety and domain capabilities. The legacy unified-workspace-experience and vscode-workspace-explorer specs inform task organization, readable evidence, note editing and workspace scope; no browser frontend is restored.

## Acceptance requirements

1. A single consistent workspace shell shows scope, current destination and contextual keyboard hints. Wide terminals show a persistent grouped navigation rail; narrow terminals retain the same destinations through a searchable switcher. Daily work (Home, Search/Memories, Ask, Notes, Sources, History, Activity, Graph, Settings) is prominent; advanced tools remain discoverable through the command palette.
2. Ctrl-K searches destinations, Ctrl-P searches all named actions, and a opens contextual actions. Typing narrows the palette; arrows/Enter choose and Esc returns without changing scope or data. Sidebar focus and active screen are visibly distinct. Navigation never steals printable input from a composer/form or discards a running mutation.
3. Home presents useful counts, recent knowledge and visible next actions. Notes, memories, sources and saved history use readable records with state/provenance, bounded list scrolling, and side-by-side preview/detail when space permits. Narrow layouts preserve list/detail access. A local filter and notes active/trash switch do not mutate records or broaden retrieval scope.
4. Ask opens directly into a question composer. Retrieval options are advanced controls with Graph Auto as the initial choice. Responses distinguish grounded context, durable memories, weak context and graph routing; empty evidence offers Search/Sources recovery instead of a fabricated answer. Another question and private saved history are easy to reach. Latest Ask context survives navigation within the selected workspace.
5. New note, edit, import and other daily operations have direct contextual shortcuts. Note editing presents title and a multiline body with a visible caret; paths/properties, IDs/revisions and retrieval options are advanced controls where safe defaults/selection already exist. An editable title is honored by assembling the document's first heading consistently with the established backend contract. New-note paths are generated once and remain editable under advanced options.
6. Fields support caret insertion, Unicode backspace/delete, left/right movement, multiline paste and the existing external editor. Choice fields remain keyboard selectable. Ctrl-S reviews/runs a form; Enter retains existing review behavior. Mutations remain explicitly confirmed, retain revision/idempotency checks, mask secrets and preserve editable drafts on backend errors.
7. Typed note/memory/history/Ask presentation prioritizes useful content over transport metadata. Advanced data inspection remains available and secret redaction/sanitization applies to every view. No endpoint or stored trust meaning changes; weak context cannot be promoted visually to canonical source evidence.
8. All layouts, palettes, fields and preview/detail screens fit from 60x16 through large terminals with Unicode and long content. Focus, empty, loading, error and success states remain legible without color. Large records remain bounded/scrollable and pending/stale results cannot replace another destination or workspace.
9. Implement and verify with meaningful keyboard/model tests, real SQLite/API operations and a real PTY daily-workflow smoke. Rebuild and update the existing installed agent-memory/am binaries only after checks pass; preserve unrelated backend work, daemon state and user data/configuration.
10. The user's follow-up requires up/down/left/right navigation. Outside editing, up/down select or scroll the focused pane; right opens a selected record, then reaches the right workspace panel, and left returns from reading to the list or from the workspace panel to content. On Home, up/down choose a daily action. The workspace panel and compact switcher accept right/Enter to activate a destination. Focus labels must explain what the arrows will do. Page Up/Down scroll long records/results. Palette left closes and right opens. Loading/stale results and busy mutations retain their existing guards.
11. Follow OpenCode's terminal interaction/layout direction: subdued neutral panels and accent edges, compact session header, prominent Home actions, readable Ask transcript above a framed bottom composer, right-side workspace/context panel on wide terminals, and a bounded command-palette dialog. Retain Agent Memory's exact service capabilities and evidence classifications. Inside multiline inputs, up/down move the caret between text lines while preserving the desired column; left/right edit text, Tab/Shift-Tab move fields, and Ctrl-Up/Down offer explicit field movement. No arrow may submit a mutation or lose a draft.
12. Agent Memory serves all registered projects. The launch picker and Workspaces screen must show the available projects and their memory counts, distinguish unavailable counts from zero, identify the current project, and explain that Enter opens that project's data. Counts use read-only bounded queries against each registered path, scoped to its project, without migrations or creating a missing database. Empty Memories/Search screens offer visible access to all projects and capture/import actions. The selected project and its memory count remain easy to see. Registered database paths are authoritative for local CLI/TUI defaults; explicit database overrides remain authoritative. Local switching finds the registry independently of the selected database's directory. Query and mutation scope remains the selected project; no automatic cross-project content query or data copy is introduced.
