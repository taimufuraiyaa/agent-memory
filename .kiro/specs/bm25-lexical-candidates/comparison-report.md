# BM25 lexical comparison report

Branch `feature/bm25-lexical-candidates`, generated 2026-10-12 by `TestLexicalComparison`
(`internal/application/lexical_eval_test.go`). Two full runs gave the same quality
numbers to within one query; the second run is reproduced below. Latency was measured on a
shared machine at a load average above 200, so absolute milliseconds are inflated and noisy.
Arms ran interleaved per query, so relative comparisons are meaningful and absolute values are not.

## Decision

**Keep the memory stream flagged off (`AGENT_MEMORY_LEXICAL_MODE=off`) and do not promote it to default yet. BM25 for library passage search now has its own rollout flag (`AGENT_MEMORY_PASSAGE_RANKING_MODE`, default off, task 9) and is the first candidate for promotion: its comparison is lexical against lexical, so the missing real embedder does not weaken it.**

| Question | Answer from this evidence |
|---|---|
| Does the lexical signal improve top-10 retrieval on identifier and distinctive-keyword queries? | Yes, by a large margin: identifier R@1 37% to 92% (weight 0.25) or 99% (weight 0.5); keywords R@1 37% to 96%. |
| Does candidate-only (weight 0) help? | No. Results are identical to the current hybrid. The value comes from the lexical ranking signal, not from adding candidates. |
| Does it beat the legacy passage scan? | Yes on every family: overall R@1 34% to 67%, identifier R@1 9% to 99%, p50 13.5 ms to 2.3 ms on 2.5k passages. |
| Does the exact-term stream carry its weight on this corpus? | No: `hybrid current` equals `vector` on every metric, and exact-term alone reaches 4-8% recall. This corpus has no curated explicit keywords, so this is not proof about production data. |
| What does it cost? | About +1.5 ms per memory write in the second run (1.6 to 3.2 ms; +3.8 ms in the noisier first run) and about +1.1 KiB of database per memory (58.6% on memory rows only; less once vectors are included). Hybrid p50 rose about 9 ms relative to lexical off under the same load. |
| Is it safe to turn on? | Fail-open and flag-gated; no new background flow. Not yet validated with a real embedding model, which is the gate in `docs/retrieval-ablation-decision.md`. |

## What this evidence does not show

- The vector arm used a hashed n-gram stand-in, not MiniLM-class embeddings. A real model will do far better on paraphrase and heading-style queries than the 0.35 MRR seen here, so the size of the BM25 gain on top of a real model is unknown. This is the main reason for not promoting.
- Queries reuse corpus tokens, which favors lexical methods. There is no paraphrase family.
- The exact-term arm had only auto-extracted terms. Production memories carry agent-curated keywords, so its production recall is likely higher than shown. Removal of `memory_terms` or the Bloom machinery is **not** supported by this report and should not happen on this evidence.
- Single corpus (this repository's Markdown, 2,509 chunks) and single machine under heavy load.

## Weight

Weight 0.5 was slightly better than 0.25 on identifier R@1 (99% vs 92%) and equal elsewhere. The default stays at 0.25 until a real-embedder run exists, because cosine scale differs between embedders.

## Follow-ups

1. Run the harness with `AGENT_MEMORY_LEXICAL_EVAL_MODEL_DIR` pointing at the real local model, and add a paraphrase family.
2. ~~Split a separate flag for passage ranking~~ done (`AGENT_MEMORY_PASSAGE_RANKING_MODE`). Promoting it to default is a separate, reviewable change gated by `docs/retrieval-ablation-decision.md`.
3. Evaluate exact-term recall on a corpus with curated keywords before any removal decision.
4. Consider document-frequency pruning or an AND-first pass for OR queries over very common terms; worst-case matching cost is linear in matched documents.

## Raw harness output

Generated by `TestLexicalComparison` on 2026-10-12.

## Setup

- Corpus: 2509 chunks cut from this repository's own Markdown (docs, specs, skills, README, SECURITY), excluding this spec.
- Queries: 450 total (identifier 150, keywords 150, heading 150), generated deterministically from the corpus; gold is every chunk that contains the query tokens (identifier/keywords) or sits under the unique heading (heading). Top-k = 10.
- Embedder: deterministic hashed word/character-trigram stand-in (384 dimensions), **not** a semantic model. Semantic floor lowered to 0.05 for all arms. Vector-arm numbers therefore do not represent MiniLM-class paraphrase quality.
- Exact-term index is populated only by automatic extraction (`locator.Extract` on content); no curated explicit keywords exist in this corpus, so that arm measures the fallback extraction path, not curated keyword recall.
- Query construction favors lexical methods (queries reuse corpus tokens); there is no paraphrase family. Treat absolute numbers as a lexical-component comparison, not an end-to-end quality claim.
- Corpus load (memories, vectors, terms, triggers): 32.094s.
